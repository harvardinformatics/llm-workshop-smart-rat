# Claude organization: Organizing an Agent-Assisted Project

# Part A — Issues & solutions

## Exploratory analysis & Deliverables

When we get data, it is rare that we know exactly what we want to do with it or what story we want to tell. Often, we will start working with data down different tracks before finding the one that sticks. This part of data analysis is the exploratory one. Exploratory data analysis generates *a lot of artifacts* that may or may not make it through to the final product/deliverable and certainly not without some modification or polishing. Exploratory analysis can quickly **bloat** your project directory, leading to confusion and lost time backtracking and this is made even worse when combined with some of the annoying tendencies of GenAI assisted coding. 

Once you have done a bit of analysis, you may want to share your data with a colleague or prepare a final version to slot into the publication. These are your deliverables. However, the path to getting to your cool answer/figure/result can be difficult to trace when you did not do the work of writing the logic that got you there. Then there's the issue of whether anyone but you can run or understand how the deliverable was created. This leads to issues of **provenance** and **reproducibility**. 

Below I've listed a few issues I've encountered when using GenAI for data analysis. This is by far not exhaustive and you may or may not experience the same issues or might prioritize different ones, but the idea is to get you thinking about how you might want to adjust the way you work with GenAI to anticipate issues. 

## 0. Not knowing what to delete, fear of losing data, information, etc. 

We're starting with this issue because the solution underpins a bunch of stuff that follows. Informatics has previously taught workshops on git/GitHub as a way to version control your code and backup your code. It was always important and it's even more important now. 

**Version control with git** saves a *snapshot* of your code base so that you can time travel to previous versions. That way you don't have to write things like `script_versionA.py` and `script_versionB.py` and just have a single `script.py`, keeping your working directory clean. 

**GitHub** is a way to back up your version controlled code base. *NOTE* it is NOT for backing up your DATA, just your CODE/small TEXT files. 

Git can have a bunch of confusing commands and if you are not familiar, it might seem intimidating. Also people aren't the best at writing descriptive commit messages. The good news is a GenAI agent can help you with all that if you give it the right permissions. 

You don't need to memorize any git commands. Ask for what you want in plain English and read what comes back. Start here:

```
Am I in a git repository? Show me git status and explain in plain English what it's telling me.
```

And when you've finished something worth keeping:

```
Show me what changed since the last commit, explain it, then write a commit message describing what changed and why. Show me the message before you commit.
```

The one part you shouldn't hand off is reading the diff before the commit lands. That's your chance to notice the agent edited a file you didn't ask it to touch — and it costs you thirty seconds.

One annoyance: Claude will ask permission every single time it runs `git status` or `git diff`, which gets old fast. We fix that with a permission rule in Part B.

## Four (more) ways agent-assisted projects go wrong

### **1. The agent doesn't know which version of the data to use.**

I have often had the issue where I'm several exploratory sessions deep and have created multiple versions of intermediate files from the raw data using different parameters. Between asking the LLM to do comparisons of the same analysis on different versions of the files and moving on to the next step, the GenAI agent silently makes decisions about which intermediate file gets pulled into which script and I have no idea it's happening. So I'll sometimes get a result that is totally wrong because the script was run on a csv that is not correct or is deprecated. 

**Solutions:**

- For small datasets: always regenerate from the raw data. If intermediate files are quick and cheap to make, don't keep them at all and only keep the code the generates them. That way, the provenance of each decision is a series of scripts/functions.
- Keep each set of intermediate files in its own exploratory folders. For example, if I'm testing out different ways of pairing complaints to devices, I'll keep separate named folders for each and direct Claude to deposit all relevant scripts and outputs inside those folders.
- Only one writer per file. Each file is only generated by a single script, and shares the same name as that script. 

The above solutions will contribute to bloat, but more stuff below will correct that. 

### **2. Patches on top of patches make for convoluted methods.**

In my experience, the way we interact with GenAI can have a bias towards *extending* over *replacing*. You'll ask it to fix X about an analysis, then Y, then Z, and pretty soon you have to chain together 5+ scripts to get to the figure you like. Meanwhile, the decisions that you and the AI make are buried in the chat history and not well documented. It's important to occasionally zoom out and rethink the approach starting from scratch to make a more coherent path from A to B. 


**Solutions:**

- Once you know the answer, throw away the path:

```
I know the answer now. Ignore the scripts we wrote getting here. Starting from data/ and the question, write the shortest script that produces this result.
```

- Start with a fresh session (`/clear`) and restate your analysis from top to bottom and plan a shorter path.
- Record the silent decisions the LLM has made as well as your own decisions so that you can examine them and throw away ones that are unnecessary.
- Write the methods *in your own words* and check it against what the LLM actually did. You'll catch steps that could be consolidated/thrown out or you'll catch misunderstandings between what you *think* happened and what *actually* happened. 


### **3. You can't tell what's safe to delete.**

This is a problem common to data analysis whether or not you are using GenAI. However, when you've got an agent that is generating 4+ files for every prompt you feed it, that can really exacerbate the problem. At least when you're manually making everything you have a mental model of what is what. 

**Solutions:**

- Regularly run file audits so you know what files exist and what they do. LLM can help you with this. We've included an `/audit-files` command that you can try using. 
- A file can go if it's regenerable by a script you can name, **or** it's in git history and nothing depends on it.
  - regularly deprecate your experiments/explorations after they've been committed to git. You can always rerun them.

### **4. You can't carve off a piece for a collaborator without refactoring first.**

Doing exploratory data analysis involves getting feedback from collaborators, peers, and PIs. We often want to share part of an analysis, like a report, a few figures or stats, or maybe the files themselves. However, it's hard to know how much to hand over and whether there is enough information for collaborators to reproduce your result (or if you could reproduce your result). 

**Solutions:**

The instinct is to make everything reproducible from the raw data, but that's rarely realistic. Analyses have a lot of components, and the raw data is often far too big to hand anyone. The goal instead is to make **where you cut the chain** a deliberate choice rather than something you discover halfway through packaging it up.

- **Organize by question, not by file type.** The scripts answering one question form one numbered chain. That chain is the thing you carve off — you can only hand over a unit you can point at.
- **Every script declares its inputs and outputs in its header** (the convention below). That makes the dependencies of any script traceable: follow the `Inputs:` lines backwards until you hit something you didn't produce. Ask Claude to walk it for you.
- **Cut wherever regenerating gets expensive.** If a step is cheap to recompute, hand over the scripts and let your collaborator rebuild it. If it's slow or huge, hand over the *intermediate file at the cut*, plus the script that wrote it and the decisions behind it. A handoff is a boundary plus a provenance story for whatever crosses it — not a copy of the whole project.
- **Keep paths to big data in one place.** One config line or variable at the top of the chain, never absolute paths sprinkled through scripts. A collaborator whose data sits on different storage then edits one line instead of hunting.

# Part B — Customizing Claude to help

Claude **cannot read** `orientation/` — that's denied in `.claude/settings.json`. So nothing in this document reaches the agent unless you write it down somewhere it can see.

You have several places to write it, and they differ in *when* they apply:

- **`CLAUDE.md`** — loaded at the start of every session, without you asking. This is where standing rules go: things that should be true on every turn.
- **`.claude/commands/` and skills** — run only when you invoke them (`/audit-files`). Right home for a procedure with several steps that you want to fire deliberately; useless for governing default behavior, since an uninvoked command does nothing.
- **`.claude/settings.json`** — permissions, enforced by the harness whether or not the agent cooperates. This is the only one that isn't a request.

All three survive `/clear`. Match the rule to the mechanism: a default belongs in `CLAUDE.md`, a procedure in a skill, a hard boundary in `settings.json`.

**How to use the rest of this document:** each section below ends with a block to add to your `CLAUDE.md`. Add it *then*, not at the end — you'll finish the day with a file you wrote and understand instead of one you pasted. Edit the wording as you go. The rules should be yours.

## A thoughtful project layout

Project organization is the first step to being able to distinguish between cruft and important files. 

```
workshop/
├── .claude/
│   ├── settings.json          ← hard rules for the agent; you can extend it
│   └── commands/
│       └── audit-files.md     ← example command. Try running it with `/audit-files`!
├── data/raw/                  ← read-only. the only source.
│                                ↓  We will create the below together ↓
├── CLAUDE.md                  ← suggestions for the agent for every chat
├── .gitignore
├── analysis/
│   ├── decisions.md           ← append-only decision log, can be automated
│   ├── scripts/
│   │   ├── 01_example.R
│   │   └── 02_example.R
│   ├── outputs/               ← regenerable; one writer per file
│   └── report.md              ← or a jupyter notebook or a Rmarkdown. 1 per analysis. 
├── analysis_notebook.md       ← equiv to your lab notebook in wet lab. Write in your own words 
└── scratch/                   ← Exploratory; gitignored; on the actual /netscratch/ if working on cluster
```

- The numbered prefix is the run order, and each script's outputs share its name (`02_example.R` → `outputs/02_example_output.csv`). That's what lets you tell at a glance what produced a file, and therefore whether it's safe to delete.
- There is no plan file. Your question goes at the top of `CLAUDE.md`; the choices you make on the way to answering it go in `decisions.md`. Both accumulate as you work.

### DO THIS NOW:

* Re-do your project directory to look like the above. 
* Move your previous analysis into scratch.
* Use `/init` to make a barebones CLAUDE.md. We will keep adding to it as we go.
* Add this first block to it — your question, and the rules that make the layout above stick:

```markdown
# Project rules

## The question
- (one sentence — e.g. "Do areas with more active smart boxes see fewer rodent complaints?")
- Keep it current. If the question changes, change this line first.

## Data
- `data/` is read-only. Never write, edit, or move anything in it.
- Read only from `data/`. Do not load intermediate files unless I name one explicitly.
- Every file we create has exactly one script that produces it.

## Code
- One question per script, numbered in run order.
- Outputs go to `analysis/outputs/` and share the script's name.
- Relative paths only, never absolute.
```

* Then make "data is read-only" a fact rather than a hope. Open `.claude/settings.json` and extend the `deny` list:

```json
{
  "permissions": {
    "deny": ["Read(./orientation/**)", "Write(./data/**)", "Edit(./data/**)"]
  }
}
```

`CLAUDE.md` is a request the agent can forget. A permission rule it cannot.

## From `scratch/` to `analysis/`

The two directories are how you can distinguish between cruft and keep. 

Do all of your exploratory stuff in the scratch directory, which can be as disorganized as you want, and then promote good ideas into the analysis directory. This works because you only have to expend effort organizing stuff once in a while (maybe at the end of a session?) rather than constantly. Plus, consciously promoting important results into a separate self contained directory will automatically make sure that the important work is reproducible *and that you understand each component*. 

Promotion is a **rewrite**, not a simple move. Claude will consolidate the scripts that produced the result and refactor them and put them in the `analysis` directory, then re-run them (unless it's too computationally heavy) to make sure the results are identical. Nothing in `analysis` should reference anything from `scratch`. 

This is the point where Claude will write up the steps, so you can read it and approve and think about it. 

### DO THIS NOW:

* Use Claude to make a **promote** skill that does the above. Check the resulting skill manually. Below is a possible prompt to use:

```
Write me a skill called "promote". When I say /promote <something in scratch/>, it should:

1. Ask me which question this result answers, if it's not obvious.
2. NOT move or copy the scratch scripts. Starting from data/ and that question, write the
   shortest script that produces the result, into analysis/scripts/, numbered in run order.
3. Give it this header:
      # <filename>
      # Question / Inputs / Outputs / Decisions
4. Write its outputs to analysis/outputs/ under the script's name.
5. Re-run it and compare every number against the scratch version. Show me the comparison.
   If anything differs, stop and tell me — don't fix it silently.
6. Leave the scratch version alone. I'll delete it myself.
7. Show me the plan before writing any files.

Then show me the skill file you wrote and tell me where it lives.
```

* Test it on a part of your previous analysis. Tweak the skill if it doesn't suit you.
* Add the default and the boundary to your CLAUDE.md:

```markdown
## Code (add to the block you already have)
- New code goes in `scratch/` by default. Only write into `analysis/scripts/` when I say "promote".
- Nothing in `analysis/` may read from `scratch/`.
```

Why both? The skill only fires when you type `/promote`. It can't set the *default* — and if nothing says otherwise, Claude will write straight into `analysis/scripts/` on an ordinary prompt and the whole scratch/analysis distinction quietly collapses. So the default is a standing rule in `CLAUDE.md`; the multi-step rewrite lives in the skill, where a long procedure that only matters occasionally belongs.

## Track the decisions, not just the results

Claude makes a lot of silent decisions when you let it just run things and these may not be recorded in a way that is easy to recover (i.e. they may be buried in chat logs or transcripts or plan docs). You also make decisions when Claude prompts you or when you are evaluating the results. It's important to keep track of these in one place, beyond just recorded it long-form in your lab notebook. Decisions also have reasons behind them that may get lost to time, so it's important to also record *Why* something happened.

This is **not** your journal. The journal is reflection on how you prompted, written by hand and deliberately slowly. A decision log is the analytical choices themselves — append-only, boring, and safe to automate.

### DO THIS NOW:

Add to your CLAUDE.md instructions for logging decisions in `decisions.md`:

```markdown
## Decisions
- Log every analytical choice to `analysis/decisions.md` — mine as well as yours.
- When I give you a choice (a threshold, which rows to drop, which test), append it before you
  write the code, marked `decided by: me`.
- When I leave a choice open and you pick a default, say so in chat and append it marked
  `decided by: agent`. Do not pick quietly.
```

`decisions.md` then looks like this:

```
| Date | Choice | Alternatives | Why | Decided by |
|---|---|---|---|---|
| 2026-09-08 | Dropped complaints before 2016 | keep all years | the 2014-15 gap is a reporting artifact, not a rat-free period | me |
| 2026-09-08 | Compared within 500 m of a device | neighborhood polygons; 1 km | — | agent (default) |
| 2026-09-08 | Counted one row per deployment, not per device | dedupe on serial_number | a redeployed device is a different intervention | me, after asking the agent to critique deduping |
```

- Log the choices you make too, not just the agent's. A log containing only the agent's defaults
  implies you made every other choice deliberately — and later you can't tell a decision from an
  accident in either direction.
- Payoff: this is what makes deleting the patch chain **non-lossy**. It also writes your report's
  limitations section for you, and it accumulates as you work rather than being filled in up front.
  - This is a `CLAUDE.md` rule and not a slash command on purpose. A command only fires when you
    remember to type it, and the decisions you most need logged are exactly the ones you didn't
    notice being made. Logging has to be continuous to be worth anything.
  - A hook could enforce it, but expect to spend session time debugging JSON. Not recommended today.


## Enforce descriptive script headers

Below is an example header of a script that summarizes (for you and the agent) what the purpose of the script was. Put it in your CLAUDE.md as a template so that scripts are more readable at a glance. 

```r
# 02_complaints_near_boxes.R
# Question:  do complaints fall off with distance to the nearest active device?
# Inputs:    data/raw/rodent_311.csv, data/raw/smart_rat_boxes.csv
# Outputs:   analysis/outputs/02_complaints_near_boxes.csv
# Decisions: active devices only; complaints from 2016 on — see analysis/decisions.md
```

`Inputs:` and `Outputs:` give you the dependency graph four lines at a time. That's what makes deciding where to cut for a handoff — and what's safe to delete — mechanical rather than a judgment call, and it's what `/audit-files` reads instead of trying to comprehend your R or Python.

### DO THIS NOW:

Add the rule and the template to your CLAUDE.md:

```markdown
## Code (add to the block you already have)
- Every script starts with this header, filled in, using the script's comment syntax:

      # <script filename>
      # Question:  <the one question this script answers>
      # Inputs:    <every file this script reads>
      # Outputs:   <every file this script writes>
      # Decisions: <choices that affect the result — see analysis/decisions.md>

- If you can't fill in the `Question:` line, the script isn't ready to leave `scratch/`.
- Keep the header current when the script changes. A stale `Inputs:` line is worse than none.
```

## Git, through Claude

If you don't know git, the agent is your interface. You still need to know what it's doing.

First, stop the permission prompts. Open `.claude/settings.json` again — the `deny` entries are the ones you added earlier, the `allow` array is what's new:

```json
{
  "permissions": {
    "deny": ["Read(./orientation/**)", "Write(./data/**)", "Edit(./data/**)"],
    "allow": ["Bash(git status:*)", "Bash(git diff:*)", "Bash(git log:*)"]
  }
}
```

Allow only the **read-only** git commands here. `commit`, `push`, and `reset` change history or your tree — keep those prompting so you see them coming.

- Commit at each answered question, not at the end of the day. That's your undo.
- **Ask Claude to explain the diff before it commits.** This doubles as a review of what the agent
  changed in your tree while you were reading its prose.
- Write a `.gitignore` — ask Claude, then check it yourself:

```
scratch/
analysis/outputs/
.venv/
__pycache__/
.Rhistory
.RData
.DS_Store
```

- Committing outputs is a real tradeoff, not an obvious call. Argue about it in your group.
